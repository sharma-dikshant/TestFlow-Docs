# API Design Specification — v1 (Current Implementation)

## Base URL

```text
/v1
```

All controllers are prefixed `v1/*` (e.g. `v1/auth/login`, `v1/assessments`). Swagger/OpenAPI docs are served at `/api/docs`, protected by HTTP Basic Auth (`SWAGGER_USER` / `SWAGGER_PASS` env vars).

## Auth Model

Every route passes through three global guards in order: `JwtAuthGuard` → `RolesGuard` → `PermissionGuard`. A route is public only if annotated `@Public()`. `RolesGuard` is currently a no-op everywhere (`@Roles()` is unused). `PermissionGuard` only gates routes annotated `@Permissions('resource:action')` — these are marked in the tables below. Everything else that isn't `@Public()` requires only a valid Bearer access token.

## Auth Module (`/v1/auth`)

| Method | Endpoint | Auth | Description |
| ------ | -------- | ---- | ----------- |
| POST | `/v1/auth/signup` | Public | Register a new user account |
| POST | `/v1/auth/login` | Public | Login with email or username + password |
| POST | `/v1/auth/refresh` | Public | Rotate refresh token for a new access/refresh pair |
| GET | `/v1/auth/me` | Bearer | Get the logged-in user's profile |
| POST | `/v1/auth/logout` | Public* | Invalidate a refresh token |

\* `/logout` is `@Public()` — it authenticates by validating the refresh token in the body, not the access token.

There is **no OTP, OAuth, or password-reset flow implemented** — the `oauth_provider`/`oauth_id` columns exist on `users` but are never populated by any code path today.

### POST `/v1/auth/signup`

Request (`SignupDto`):

```json
{
  "firstName": "John",
  "lastName": "Doe",
  "username": "john_doe",
  "email": "john@example.com",
  "password": "Secret123!",
  "phoneNumber": "+919876543210"
}
```

Validation: `firstName`/`lastName` letters/spaces/hyphens/apostrophes only; `username` alphanumeric + underscore, 3–100 chars; `password` 8–255 chars, must contain upper, lower, digit, and special character; `phoneNumber` optional, E.164-ish pattern.

Response 200 (envelope — see [Response Format](#response-format)): `{ accessToken, refreshToken }`. Errors: 409 on duplicate email/username/phone.

### POST `/v1/auth/login`

Request (`LoginDto`): `{ identifier fields: username OR email, password }` — exactly one of `username`/`email` is required (mutually validated via `@ValidateIf`).

```json
{ "email": "john@example.com", "password": "Secret123!" }
```

Response 200: `{ accessToken, refreshToken }`. Errors: 401 on user-not-found or password mismatch.

### POST `/v1/auth/refresh`

Request (`RefreshDto`): `{ "refreshToken": "<jwt>" }`.

Server verifies the refresh JWT signature, hashes it (SHA-256), and matches it against the stored `refresh_tokens` row for that user. On success, the old row is soft-deleted and a new access/refresh pair is issued (rotation). Response 200: `{ accessToken, refreshToken }`. Errors: 401 invalid/expired/not found.

### GET `/v1/auth/me`

Bearer auth required. Response 200: `MeResponseDto` — `{ id, fullName, firstName, lastName, username, email, phoneNumber }`.

### POST `/v1/auth/logout`

Request (`LogoutDto`): `{ "refreshToken": "<jwt>" }`. Soft-deletes the matching `refresh_tokens` row(s). Always returns 200 `{ message: "Logged out successfully" }`, even if nothing matched.

## Users Module (`/v1/users`)

There is **no plain CRUD users controller.** The only HTTP surface under `users` is role assignment. `UsersService` has `findAll`/`update`/`remove` methods but none are wired to any route.

### Role Assignment (`v1/users/:username/roles`)

| Method | Endpoint | Permission | Description |
| ------ | -------- | ---------- | ----------- |
| GET | `/v1/users/:username/roles` | `users:read` | List roles assigned to a user |
| POST | `/v1/users/:username/roles` | `users:create` | Assign a role to a user (body: `{ roleKey }`) |
| DELETE | `/v1/users/:username/roles/:roleKey` | `users:delete` | Remove a role from a user |

Errors: 404 unknown username/roleKey, 409 role already assigned (POST).

## RBAC Module

### Roles (`v1/roles`)

| Method | Endpoint | Permission | Description |
| ------ | -------- | ---------- | ----------- |
| GET | `/v1/roles` | `roles:read` | List all roles |
| GET | `/v1/roles/:roleKey` | `roles:read` | Get role by key |
| POST | `/v1/roles` | `roles:create` | Create a role (body: `{ key }`) |
| PATCH | `/v1/roles/:roleKey` | `roles:update` | Rename a role's key |
| DELETE | `/v1/roles/:roleKey` | `roles:delete` | Soft-delete a role |

### Resources (`v1/resources`)

| Method | Endpoint | Permission | Description |
| ------ | -------- | ---------- | ----------- |
| GET | `/v1/resources` | `resources:read` | List all resources |
| GET | `/v1/resources/:resourceKey` | `resources:read` | Get resource by key |
| POST | `/v1/resources` | `resources:create` | Create a resource (body: `{ key }`, e.g. `assessments:create`) |
| PATCH | `/v1/resources/:resourceKey` | `resources:update` | Rename a resource's key |
| DELETE | `/v1/resources/:resourceKey` | `resources:delete` | Soft-delete a resource |

### Role Permissions (`v1/roles/:roleKey/permissions`)

| Method | Endpoint | Permission | Description |
| ------ | -------- | ---------- | ----------- |
| GET | `/v1/roles/:roleKey/permissions` | `permissions:read` | List resource keys granted to a role |
| PUT | `/v1/roles/:roleKey/permissions` | `permissions:update` | Replace a role's entire permission set (body: `{ permissions: string[] }`, values are resource keys) |
| POST | `/v1/roles/:roleKey/permissions/:resourceKey` | `permissions:create` | Grant a single resource to a role |
| DELETE | `/v1/roles/:roleKey/permissions/:resourceKey` | `permissions:delete` | Revoke a single resource from a role |

### Access Check (`v1/access-check`)

| Method | Endpoint | Permission | Description |
| ------ | -------- | ---------- | ----------- |
| POST | `/v1/access-check` | `permissions:read` | Direct role↔resource check (body: `{ roleKey, resourceKey }` → `{ allowed }`). Strict exact-match only — does **not** apply the `*:*` wildcard fallback that the runtime `PermissionGuard` uses; intended for admin tooling, not request authorization. |

**Default seed data**: exactly one role, `super_admin`, granted the wildcard resource `*:*` (blanket access to every permission check). 21 resource keys are seeded: `*:*` plus the CRUD matrix (`read`/`create`/`update`/`delete`) for `users`, `roles`, `permissions`, `resources`, `questions`. Any additional roles/resources must be created via these endpoints after deployment. `plans` exists as an `RbacResource` enum value but is not part of the seeded resource matrix and no controller currently applies `@Permissions('plans:...')`.

## Questions Module (`/v1/questions`)

| Method | Endpoint | Permission | Description |
| ------ | -------- | ---------- | ----------- |
| POST | `/v1/questions` | `questions:create` | Create a question |
| GET | `/v1/questions` | Public | Paginated list, filterable by `search`, `created_by` |
| GET | `/v1/questions/:id` | Public | Get question by ID |
| PATCH | `/v1/questions/:id` | `questions:update` | Update a question |
| DELETE | `/v1/questions/:id` | `questions:delete` | Soft-delete a question |

This is the only assessment-engine module that enforces RBAC permissions — `assessments` and `attempts` rely on bearer auth plus service-level ownership checks only.

### Question shape

```json
{
  "questionText": "What is the time complexity of binary search?",
  "options": [
    { "id": 1, "text": "O(n)" },
    { "id": 2, "text": "O(log n)" }
  ],
  "correctOptionId": 2
}
```

`correctOptionId` must match one of the supplied `options[].id` (custom validator `IsCorrectOptionPresent`). Filters: `GET /v1/questions?search=binary&created_by=1&page=1&limit=20`.

## Assessments Module (`/v1/assessments`)

| Method | Endpoint | Auth | Description |
| ------ | -------- | ---- | ----------- |
| POST | `/v1/assessments/generate` | Bearer | Create an assessment pre-populated with N random questions from the question bank (see note below — **not** LLM-generated) |
| POST | `/v1/assessments` | Bearer | Create an empty assessment shell (no questions yet) |
| GET | `/v1/assessments` | Public | Paginated list with filters |
| GET | `/v1/assessments/me` | Bearer | List assessments created by the caller |
| GET | `/v1/assessments/:id` | Public | Get assessment by ID |
| PATCH | `/v1/assessments/:id` | Bearer, creator-only | Update assessment |
| DELETE | `/v1/assessments/:id` | Bearer, creator-only | Soft-delete assessment |
| POST | `/v1/assessments/:id/questions` | Bearer, creator-only | Add questions to an assessment |
| POST | `/v1/assessments/:id/check-enrollment` | Bearer | Check if the caller is enrolled |
| POST | `/v1/assessments/:id/register` | Bearer | Register (enroll) as a participant |
| POST | `/v1/assessments/:id/unregister` | Bearer | Unregister (soft-delete participation) |

Creator-only ownership is enforced in the service (`assessment.createdBy === userId`, else 403) — not via `@Permissions()`.

> **Note on `/generate`**: despite the name and Swagger summary ("Generate an AI-powered assessment"), this endpoint does not call an LLM. It draws `totalQuestions` random rows from the existing `questions` table (`ORDER BY RANDOM() LIMIT n`), snapshots them onto the new assessment, and auto-enrolls the creator as the first participant. An unused interface (`GeneratedQuestion`) exists at `src/ai/interfaces/` with zero consumers — this appears to be scaffolding for a not-yet-built AI integration.

### POST `/v1/assessments/generate`

```json
{
  "description": "GATE CS mock test — Data Structures",
  "startTime": "2026-07-20T09:00:00Z",
  "endTime": "2026-07-20T11:00:00Z",
  "duration": 120,
  "maxParticipants": 100,
  "totalQuestions": 25,
  "positiveMark": 2,
  "negativeMark": 0.5
}
```

Response 200: `{ message: "Assessment generated successfully" }` (creates real resources despite the 200 status).

### POST `/v1/assessments`

Same shape as `generate` except fields are named `maxTotalQuestions`, `correctMarks`, `incorrectMarks` (no `totalQuestions`/`positiveMark`/`negativeMark`), and it creates an empty shell — no questions, no auto-enrolled participant.

### POST `/v1/assessments/:id/questions`

```json
{
  "questions": [
    { "questionId": 12, "correctMarks": 2, "incorrectMarks": 0.5 }
  ]
}
```

Rejects duplicate `questionId`s in the payload, non-existent question IDs, questions already assigned to this assessment, and payloads that would exceed `maxTotalQuestions - currTotalQuestions` remaining capacity.

### GET `/v1/assessments` — filters

```text
GET /v1/assessments?status=upcoming|ongoing|completed   (derived from start_time/end_time, not stored)
GET /v1/assessments?created_by=1
GET /v1/assessments?search=javascript
GET /v1/assessments?start_time=gte:2026-07-01
GET /v1/assessments?sort=created_at|start_time|end_time&order=asc|desc
GET /v1/assessments?popular=true
GET /v1/assessments?page=1&limit=20
```

## Attempts Module (`/v1/attempts`)

This module is the sole owner of the attempt/submission/evaluation flow (see [Architecture](../architecture.md#4-assessment-engine-flow) for the legacy-dead-code note in `assessments/dto` and `assessments/enums`).

| Method | Endpoint | Auth | Description |
| ------ | -------- | ---- | ----------- |
| GET | `/v1/attempts/me` | Bearer | Paginated list of the caller's attempts, filterable by `status` |
| POST | `/v1/attempts/:assessmentId/start` | Bearer | Start (or resume) an attempt; returns `{ uid }` |
| GET | `/v1/attempts/:attemptUid/questions` | Bearer, owner-only | List questions in the attempt with `selectedOptionId` if answered |
| GET | `/v1/attempts/:attemptUid/questions/:assessmentQuestionId` | Bearer, owner-only | Full detail (text + options) of one question |
| PUT | `/v1/attempts/:attemptUid/responses/:assessmentQuestionId` | Bearer, owner-only | Upsert a response (body: `{ optionId }`) |
| DELETE | `/v1/attempts/:attemptUid/responses/:assessmentQuestionId` | Bearer, owner-only | Delete a saved response |
| POST | `/v1/attempts/:attemptUid/submit` | Bearer, owner-only | Submit the attempt; triggers async evaluation |
| GET | `/v1/attempts/:attemptUid/result` | Bearer, owner-only | Get evaluated result with per-question breakdown |

Ownership is enforced by comparing `attempt.userId` to the caller (403 `ForbiddenException` otherwise); unknown `attemptUid` returns 404.

### POST `/v1/attempts/:assessmentId/start`

Returns the existing attempt's `uid` if the user already has one for this assessment (one attempt per user per assessment, DB-enforced via a unique constraint on `(user_id, assessment_id)`). Otherwise creates a new `assessment_attempts` row (`status: IN_PROGRESS`, `totalQuestions` snapshotted from `assessment.currTotalQuestions`).

### PUT `/v1/attempts/:attemptUid/responses/:assessmentQuestionId`

```json
{ "optionId": 2 }
```

Requires `attempt.status === IN_PROGRESS` and the assessment window to currently be open (`startTime <= now <= endTime`, checked live). Computes `isCorrect` and `marksAwarded` immediately (`marksAwarded = isCorrect ? +correctMarks : -incorrectMarks`, using the question's snapshotted marking scheme) and upserts the response row.

### POST `/v1/attempts/:attemptUid/submit`

Conditionally updates `status: IN_PROGRESS → SUBMITTED` (rejects double-submit with 400 if already submitted), marks the participant `COMPLETED`, and fires `EvaluationService.evaluate()` **without awaiting it**. Returns `true` immediately — evaluation (aggregating response rows into `score`/`attemptedQuestions`/`correctResponses`/`incorrectResponses`, then flipping status to `EVALUATED`) completes shortly after, asynchronously.

### GET `/v1/attempts/:attemptUid/result`

Returns 400 `"Attempt has not been evaluated yet"` if `status !== EVALUATED` — there's a brief window right after submit where this can happen since evaluation is async.

## Commerce — Plans (`/v1/plans`)

| Method | Endpoint | Permission | Description |
| ------ | -------- | ---------- | ----------- |
| GET | `/v1/plans` | Public | Paginated list of active plans, each with its current version + features |
| POST | `/v1/plans` | `plans:create` | Create a plan + its version 1 |
| POST | `/v1/plans/:planId/versions` | `plans:create` | Create a new version for an existing plan (auto-demotes the prior current version) |
| PUT | `/v1/plans/:planId/versions/:versionNo` | `plans:update` | Update pricing fields of an existing version in place (does not affect `isCurrent`) |
| POST | `/v1/plans/:planId/versions/:versionNumber/features` | `plans:create` | Add a feature to a plan version |
| PUT | `/v1/plans/:planId/versions/:versionNumber/features/:featureId` | `plans:update` | Update an existing feature |

### POST `/v1/plans`

```json
{
  "name": "PRO",
  "description": "Full access to assessment creation and analytics",
  "price": 999,
  "currency": "INR",
  "billingCycle": "MONTHLY",
  "effectiveFrom": "2026-07-15T00:00:00Z"
}
```

Server generates a unique 10-character `code` (e.g. `7K9XQPLM2R`, drawn from an ambiguity-free alphabet) — this is the stable public identifier used at checkout, distinct from the numeric `id`.

### GET `/v1/plans` — filters

```text
GET /v1/plans?name=PRO
GET /v1/plans?page=1&limit=20
```

Only ever returns each plan's **current** version (`is_current = true`) — historical versions are not exposed via this listing endpoint.

## Commerce — Subscriptions (`/v1/subscriptions`)

| Method | Endpoint | Auth | Description |
| ------ | -------- | ---- | ----------- |
| POST | `/v1/subscriptions/checkout` | Bearer | Start checkout for a specific plan code + version |

This is the **only** subscriptions endpoint currently implemented — there is no list/get/cancel/renew endpoint yet, despite `CreateSubscriptionDto`/`UpdateSubscriptionDto` existing as unused placeholders.

### POST `/v1/subscriptions/checkout`

```json
{ "planCode": "7K9XQPLM2R", "version": 3 }
```

Both `planCode` and `version` are required — this pins an exact price/feature snapshot rather than "whatever is current," so a user can be checked out against an older (but not-yet-expired) version.

Validation sequence: plan exists (404) → plan is active (422) → that specific version exists for the plan (404) → version's `effectiveUntil` hasn't passed (422) → caller has no existing `ACTIVE` subscription for this plan (409, note: a `PENDING` subscription for the same plan does **not** block a second attempt).

Response 201:

```json
{
  "subscription": { "id": 10, "planVersionId": 3, "status": "PENDING", "startsAt": "...", "expiresAt": "..." },
  "order": { "id": 22, "status": "PENDING", "totalAmount": 999, "currency": "INR", "provider": "RAZORPAY", "providerOrderId": "chk_...", "expiresAt": "..." }
}
```

`order.providerOrderId` here is a placeholder (`chk_<uuid>`), **not** a real Razorpay order id yet — checkout only stages the order (default 30-minute payment window via `CHECKOUT_ORDER_TTL_MINUTES`). The real Razorpay order is created by the next call, `POST /v1/payments/razorpay/create`.

## Payments Module (`/v1/payments`)

| Method | Endpoint | Auth | Description |
| ------ | -------- | ---- | ----------- |
| POST | `/v1/payments/razorpay/create` | Bearer | Create a real Razorpay order for a pending TestFlow order, and a matching `PENDING` payment record |

This is the only endpoint — `CreatePaymentDto`/`UpdatePaymentDto` exist as empty unused placeholders (no generic payments CRUD).

### POST `/v1/payments/razorpay/create`

```json
{ "orderId": 22 }
```

Validates the order belongs to the caller (403), is `PENDING` (422 if expired, 409 if already paid), then calls Razorpay's `orders.create` API (amount converted to paise) and persists a `payments` row. Idempotent: a repeated call against the same pending order reuses the existing pending payment rather than creating a duplicate Razorpay order.

Response 201:

```json
{
  "paymentId": 5,
  "orderId": 22,
  "amount": 999,
  "currency": "INR",
  "razorpayOrderId": "order_MnO4x...",
  "razorpayKeyId": "rzp_test_...",
  "status": "PENDING"
}
```

The frontend uses `razorpayOrderId` + `razorpayKeyId` to open the Razorpay Checkout widget client-side.

## Webhooks Module

| Method | Endpoint | Auth | Description |
| ------ | -------- | ---- | ----------- |
| POST | `/webhooks/razorpay` | Public, HMAC-verified in-service, hidden from Swagger | Receives Razorpay payment webhook events |

Not versioned under `/v1` — mounted at the app root since it's called by Razorpay's infrastructure, not a versioned client.

Signature verification happens **inside** `WebhooksService` (not a guard/middleware): missing `x-razorpay-signature` header → 401; invalid HMAC (`RazorpayService.verifyWebhookSignature`, verified against `RAZORPAY_WEBHOOK_SECRET`) → 401.

Only `payment.captured` and `payment.failed` events are processed; anything else is logged and ignored. Idempotency is enforced via a `webhook_events` row keyed on `event_id = "{event}:{razorpayPaymentId}"` — a redelivered event with `processed = true` already recorded is a no-op.

- **`payment.captured`** → `Payment.status = SUCCESS`, `Order.status = PAID`, and — only if `order.resourceType === SUBSCRIPTION` — a direct `Subscription.status = ACTIVE` update (cross-module, explicitly TODO-flagged in code as a temporary shortcut pending an event-driven refactor for other resource types like `AI_CREDITS`).
- **`payment.failed`** → `Payment.status = FAILED` only. `Order` and any linked `Subscription` are left untouched (order stays `PENDING`, allowing retry until it expires).

## Response Format

Verified against `src/common/api-response.ts`, `src/common/interceptors/response.interceptor.ts`, and `src/common/filters/http-exception.filter.ts` — this **replaces** the previously documented `{success, data, meta, error}` shape, which does not match the implementation (there is no `error` key anywhere in the codebase).

### Success

```json
{
  "success": true,
  "message": "Success.",
  "data": { "...": "..." },
  "meta": { "page": 1, "limit": 20, "total": 100 }
}
```

- `message` is always present (controllers pass a specific message via `new ApiResponse(data, message, meta?)`; a bare plain-object controller return gets the default `"Success."`).
- `meta` is present **only if** the controller explicitly passed one — it is not a fixed shape enforced by the envelope itself, though pagination endpoints consistently use `{page, limit, total}`.
- `204 No Content` responses are passed through unwrapped (no envelope).

### Error

```json
{
  "success": false,
  "message": "Insufficient permission: questions:create",
  "code": "FORBIDDEN"
}
```

`HttpExceptionFilter` catches everything (`@Catch()`, not just `HttpException`). Any extra fields present on a thrown exception's response body (besides `message`/`error`/`statusCode`) are spread flat onto the top-level error object — there is no nested `error` object. Unhandled non-`HttpException` errors are logged server-side and returned as a generic `500` with `message: "Internal server error"`.

### Validation errors

The global `ValidationPipe` is configured with `whitelist: true, forbidNonWhitelisted: true, transform: true` — unknown request fields are stripped and, if `forbidNonWhitelisted` catches an unknown field, the whole request is rejected with 400 and a `message` array from `class-validator`, joined into a single string by the filter.

## Query Standard

### Pagination (assessments, questions, plans)

```text
?page=1&limit=20
```

`limit` typically capped at 100 by DTO validation.

### Filtering

Date-range filters use an explicit operator prefix (assessments' `start_time` filter):

```text
?start_time=gte:2026-07-01
```

### Sorting (assessments only)

```text
?sort=created_at|start_time|end_time&order=asc|desc
```

### Search

```text
?search=keyword
```

Implemented on `questions` (`question_text ILIKE`) and `assessments` (`description ILIKE`).
